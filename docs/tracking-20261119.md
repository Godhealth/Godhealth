# Tracking: Google Analytics 4 and Meta (19 November 2026)

This note describes how visitor measurement works on the three GodHealth sites and what to keep in mind when changing them. It is written for whoever maintains the sites next, person or tool.

| Site | Repository and branch | What Vercel serves |
| --- | --- | --- |
| www.godhealth.org | `Godhealth`, branch `main` | the repository root |
| blueprint.godhealth.org | `Godhealth`, branch `blueprint-landing` | `ads/blueprint-landing` |
| sales.godhealth.org | `godhealth-sales-page`, branch `main` | `dist/` |

## The short version

- Nothing is loaded from Google or Meta, and nothing is stored or sent, until the visitor agrees in the cookie banner. "Statistics" switches on Google Analytics, "Advertising" switches on Meta.
- One cookie holds the choice for all three sites: `gh_cookie_consent` on `.godhealth.org`, valid for six months.
- One file talks to Google and Meta: `assets/gh-tracking.js`. Pages only load it; they contain no Google or Meta code themselves.
- Conversions also go to Meta from the server (`api/gh-events.js`, the Meta Conversions API). That part does nothing until its access token is set in Vercel.
- A purchase is counted only after Stripe confirms the payment (`api/gh-purchase.js` on the sales site).

## Files

| File | Where | What it does |
| --- | --- | --- |
| `assets/gh-tracking.js` | all three sites, identical | Loads the Google tag and the Meta Pixel after consent and sends the events listed below. |
| `assets/gh-consent.js` | all three sites, identical | Cookie banner for the Blueprint and sales pages. The main site uses its own banner in `assets/public-preferences.js`; this file then stays idle. |
| `api/gh-events.js` | all three sites, identical | Receives conversions from the page and passes them to Meta. |
| `api/gh-purchase.js` | sales site | Asks Stripe whether a checkout session was paid and reports the purchase. |
| `scripts/test-gh-events.js` | main site | Tests for the relay. |
| `scripts/check-gh-tracking.js` | main site | Checks that every public page carries the tag and the current cookie text, that versions and prices match, and which tags start where. |

The three shared files must stay identical between the sites. When one changes, copy it to the other two.

## What is measured

| Visitor action | Google Analytics event | Meta event | Also from the server |
| --- | --- | --- | --- |
| Opens a page | `page_view` (automatic) | `PageView` | no |
| Opens an offer page (sales page, product pages, Blueprint page, `/coaching`, `/personal-training`, `/nutrition-bundle`, `/blueprint`) | none | `ViewContent` | no |
| Requests the Blueprint | `generate_lead` (`lead_type` = `blueprint`) | `Lead` | yes |
| Clicks a Calendly link | `strategy_call_clicked` | `Contact` | yes |
| Clicks a WhatsApp link | `whatsapp_click` | `Contact` | yes |
| Clicks a phone or email link | `phone_click`, `email_click` | none | no |
| Clicks a link to the Stripe checkout | `begin_checkout` | `InitiateCheckout` | yes |
| Pays (thank-you page of the sales site) | `purchase` | `Purchase` | yes, by `api/gh-purchase.js` |
| Clicks through to the Blueprint site, the sales site or the Vitality Scan | `blueprint_cta_clicked`, `bundle_cta_clicked` (`thank_you_sales_click` from the Blueprint thank-you page), `scan_cta_clicked` | none | no |

Click events carry `cta_label` (the visible text of the link), `cta_section` (`header`, `footer` or the id of the section) and, where it applies, `contact_method` and `link_url`. A click is recognised by where the link leads, so navigation and footer links count too; `cta_section` tells them apart.

The browser and the server send the same event id, so Meta counts each conversion once. A purchase carries the amount Stripe charged, without tax, and the product is recognised by its list price.

## What is deliberately not measured

- **The Vitality Scan** (`kingdom-vitality-scan.html`) does not load the tracking file. The page is protected by `scripts/check-public-site.py` and shows answers about faith and health. Clicks towards the scan are counted on the other pages.
- **The private apps** (`/client`, `/coach-dashboard`, `/kingdom-capacity-assessment`, `/kca`) and any page opened with a login token or contact details in its address.
- **Meta gets nothing** from the articles under `/guides` and `/topics`, from the "page not found" page, or from the scan. Their address does not reach Meta as the previous page either: the articles and the "page not found" page tell the browser to pass on only `https://www.godhealth.org/` (rule 3 below), so the page a reader opens next loads the Pixel as usual. On a page opened from the scan, which cannot carry that instruction, the Pixel is left out for that one page view and conversions go through the server only. Google Analytics does measure the articles.
- **Anything a visitor did before answering the banner.** It is not sent afterwards. The one exception is a confirmed purchase, which is reported when the visitor agrees while still on the thank-you page.
- **Calendly bookings.** Only the click towards Calendly is visible.

Expect the numbers in Google Analytics and Meta to be lower than reality: visitors who decline or ignore the banner are not counted. Compare leads with the automation that receives them and purchases with Stripe.

Separate from the cookie choice: a Blueprint sign-up always stores the page the visitor signed up on and the campaign link that brought them there in the lead record (`landing_page`, the `utm_*` fields). The privacy policy says so. Carrying campaign details on to the next pages does depend on the "Advertising" choice.

## Address bar

On every page view, with or without a choice, the tracking file first tidies the address bar: only `utm_*` and the ad click ids (`fbclid`, `gclid`, `gbraid`, `wbraid`, `msclkid`, `_gl`) stay. Anything else, such as a newsletter subscriber id, would otherwise travel to Google and Meta inside the page address, or one page later as the previous address. The sales thank-you page is the exception: it keeps the Stripe session id until a choice is made (so a reload still works) and tells the browser to pass on only the site name instead. If the address bar cannot be tidied, no tag is loaded on that page.

## Consent

- Cookie: `gh_cookie_consent = {version: 2, analytics, marketing, updatedAt}`, shared on `.godhealth.org`.
- The version number belongs to the wording of the banner. Whenever the purposes or the companies that receive data change, change the text and raise the number in **all** of these places, in the same change:
  - `CONSENT_VERSION` in `assets/public-preferences.js`, `assets/gh-consent.js`, `assets/gh-tracking.js` and `api/gh-events.js`;
  - `data-gh-consent-version` on the banner of the main site, in `data/public-ui.mjs` and in the 29 committed pages.

  Every visitor is then asked again. A choice made under an older text never counts, and a page that still shows an older text cannot store a current "yes". `scripts/check-gh-tracking.js` fails when a page shows other cookie text than the template.
- When a visitor withdraws a choice, the tracking file removes the Google and Meta cookies and reloads the page once, so a tag that was already loaded cannot send anything more. When the choice is withdrawn in another window, the tags are silenced at once and the reload follows when the page is shown again.
- An answered "no" also removes Google and Meta cookies left from an earlier "yes" (a choice that lapsed after six months, or one withdrawn on a page without the tracking file).
- Google's advertising signals stay off. Switch them on (`googleAdSignals` in `gh-tracking.js`) only together with new consent wording and a new version number.

## Settings in Vercel

Set these under Project > Settings > Environment Variables, for **Production only**, and redeploy afterwards. Never put a value in a file.

| Variable | Project | Meaning |
| --- | --- | --- |
| `META_CAPI_ACCESS_TOKEN` | all three | Conversions API token from Meta Events Manager. Without it the relay stays silent. |
| `STRIPE_RESTRICTED_KEY` | sales | Stripe restricted key with only "Checkout Sessions: Read". Without it no purchase is counted. |
| `STRIPE_PAYMENT_LINK_ID` | sales | Optional. Limits purchases to the listed Payment Links (`plink_...`, comma separated). Leave it empty while more links are in use than you list. |
| `META_TEST_EVENT_CODE` | any | Optional and temporary, for testing. Events sent with it still count in Meta. Remove it afterwards. |
| `META_PIXEL_ID`, `META_API_VERSION` | any | Optional overrides. A value that is set but malformed switches forwarding off. |

Open `/api/gh-events` (and `/api/gh-purchase` on the sales site) in a browser to see whether the settings are in place. The answer shows true or false per setting, never a secret.

- `"forwarding": true` only says that a Meta token is present, not that Meta accepts it. After setting the token, set `META_TEST_EVENT_CODE` for a moment, trigger one event, look for it under Events Manager > Test events, and remove the code again.
- `"stripe_key_accepted": true` means Stripe accepts the key for reading checkout sessions; `false` means a wrong key or a missing permission.

The functions need Node.js 22 or newer (Project > Settings > Build and Deployment > Node.js Version). A preview deployment that fails with a Node.js error points to this setting.

## Settings in Google Analytics that the code relies on

- The Google tag starts without a `config` command (the 2026 loader, `gtm.js?id=G-...`). Checked on 19 November 2026: a test visit arrived in DebugView with `first_visit`, `session_start` and `page_view`. Check again after every change to the Google tag: open a page with `?gh_track_test=1`, accept Statistics, and look in the browser's network panel for a request to `/g/collect` with `en=page_view`. No request means Analytics receives nothing.
- Key events: `purchase`, `generate_lead`, `strategy_call_clicked`, `whatsapp_click` (the last two count once per session). Marking is not retroactive.
- Custom dimensions (event scope): `cta_label`, `cta_section`, `contact_method`, `lead_type`. `link_url` fills the built-in "Link URL".
- Enhanced measurement: form interactions off, page views on browser history changes off (otherwise every in-page anchor link counts as a page view).
- Redact data: email addresses, and the query keys the tracking file treats as sensitive, including `session_id`.
- Unwanted referrals: `stripe.com`, `calendly.com`. Add a bank or payment-redirect domain when purchase sessions show one as their source.
- Data filter "Developer traffic": active. Own visits without the test switch stay out only with an "Internal traffic" filter (Admin > Data streams > the stream > Configure tag settings > Define internal traffic).
- One stream serves three hosts, and `/` exists on all three: add the dimension Hostname to page reports.
- Retention 14 months; data sharing with Google and Google signals off.

## Settings in Meta Events Manager (dataset 4064076763888809)

- Automatic advanced matching: off. The code sends one hashed email address itself, only with the Blueprint sign-up and only after consent.
- Event setup > "Track events automatically without code": off. Create no events with the Event Setup Tool.
- Do not switch on Meta's own Conversions API set-up or a gateway next to `api/gh-events.js`; every event would then arrive twice through different routes.
- Cookie settings: first-party cookies on. The relay reads `_fbp` and `_fbc`.
- Traffic permissions: allow list with `godhealth.org`.
- Before building a campaign on Lead or Purchase, and again after the first week of traffic: Settings > "Manage data source categories" and the Diagnostics tab. Meta can restrict health and wellness data sources; plan a goal that survives a restriction (landing page views or ViewContent).
- Acceptance in Test events: only PageView, ViewContent, Contact, Lead, InitiateCheckout and Purchase appear, and each conversion shows a browser copy and a server copy with the same event id.

## How to test

- Add `?gh_track_test=dry` to any page. Nothing is sent; the browser console shows what would be sent. Works on localhost and on preview links too. `?gh_track_test=0` switches it off.
- `?gh_track_test=1` really sends. The page view and the events from this file carry the debug flag: they show in DebugView, and the data filter "Developer traffic" keeps them out of the reports. Google's own automatic events of that visit (scroll, outbound click, engagement) are not flagged.
- The switch is remembered for the browser tab. In a browser that blocks storage it only applies to the page view whose address carries it.
- `node scripts/test-gh-events.js` and `node scripts/check-gh-tracking.js` must pass, together with `python3 scripts/check-public-site.py`.

## Rules when changing the main site

1. The public pages are written by `scripts/build-public-site.mjs`, and the committed pages also contain hand edits. A change to the tags must go into the generator **and** the committed pages, so the two stay equal.
2. Each public page loads `/assets/gh-tracking.js` exactly once, directly after `/assets/public-preferences.js`. No page contains Google or Meta code of its own.
3. The articles under `/guides` and `/topics` and the "page not found" page carry `<meta name="referrer" content="origin">`, so their address is not passed on to the next page.
4. Prices are listed twice and must match: `products` in `assets/gh-tracking.js` and `PRODUCTS` in `api/gh-events.js`.
5. Browsers keep files from `/assets/` for one hour. The `?v=` part of the script address makes a change visible at once; without changing it, visitors get the new file within the hour.
6. The path rules compare the decoded address, because Vercel serves `/%67uides/x` and `/guides%2Fx` like `/guides/x`. Keep `pathMatches()` in `gh-tracking.js` and `pathBlocked()` in `api/gh-events.js` equal.
